Review this fully functional implementation of both transient notification systems in Jetpack Compose,
extracted into a standalone component. Consider why one requires a complex architectural construct,
while the other can be fired instantly into the simulation.

```kotlin
@Composable
fun MatrixCommunicator() {
    // The Global State & Scope (The Construct)
    val snackbarHostState = remember { SnackbarHostState() }
    val scope = rememberCoroutineScope()
    val context = LocalContext.current

    // The Architectural Skeleton (The Matrix Grid)
    Scaffold(
        modifier = Modifier.fillMaxSize(),
        snackbarHost = { SnackbarHost(hostState = snackbarHostState) }
    ) { innerPadding ->

        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(16.dp)
        ) {
            // The Snackbar Trigger (Red Pill)
            Button(onClick = {
                scope.launch {
                    snackbarHostState.showSnackbar(
                        message = "Operator tracking established.",
                        actionLabel = "DISCONNECT",
                        duration = SnackbarDuration.Short
                    )
                }
            }) {
                Text(text = "Take the Red Pill (Snackbar)")
            }

            // The Toast Trigger (Blue Pill)
            Button(onClick = {
                Toast.makeText(
                    context,
                    "Ignorance is bliss.",
                    Toast.LENGTH_LONG
                ).show()
            }) {
                Text("Take the Blue Pill (Toast)")
            }
        }
    }
}
````

Why do we need to launch a CoroutineScope to show a Snackbar, but a Toast just fires instantly without

## The Notification Simulation
Imagine your application is the Matrix.

A `Toast` is a minor glitch in the simulation—a fleeting green line of code that passes by
unnoticed by the system's architecture. It is a brief, non-interruptive message.

A `Snackbar` is an Agent appearing in the crowd. It provides information and an optional action
(like a "DISCONNECT" button), persisting just long enough for you to interact with it before
disappearing back into the code.


## The 4W2H Data Logistics Breakdown
Let's dissect how these notifications operate within the system architecture according to the 4w2h model.
As engineers, we must answer 6 fundamental questions, known as the 4W2H model:
What?, Where?, When?, Who?, How?, and How Long?



### 0. WHAT are we processing?
Both notifications handle "The Sticky Note" (Primitives).
They process short, simple information, like a string, which is volatile and easy to handle.

### 1. WHERE does the data live?
A `Toast` relies on "The Pocket" (Local Variables). It fires locally and the app instantly forgets about it.
A `Snackbar` utilizes "The Office" (Global State). The `SnackbarHostState` acts as the manager's global
corkboard, managing a strict queue so multiple Snackbars don't overlap on the screen.

### 2. WHEN do we cook?
Both utilize "The Drive-Thru" paradigm. The computer does nothing until the application explicitly asks
for the next element, generating data strictly on demand when the user clicks.

### 3. WHO sets the pace?
The interaction is driven by the Pull Model ("The Waiter").
You are in full control and explicitly trigger the event.

### 4. HOW does the UI know?
A `Toast` operates via "The Silent Ledger" (Regular variable). It bypasses Compose entirely and asks
the Android OS directly.

The `Snackbar` is heavily reliant on "The PA System" (State). SnackbarHostState actively broadcasts its
visibility status to the Scaffold, forcing the UI to redraw and animate the component into view.

### 5. HOW LONG does it survive?
Both live strictly in "Short-term Memory" (Volatile memory). If you rotate the device, restarting
the application is like the waiter tripping—the data is lost forever.

## The Construct: Coroutines & Scope
To deploy a Snackbar, we must manipulate time within the simulation using Coroutines.
- **Coroutine** (The Operator): A lightweight thread that allows you to execute asynchronous
code sequentially without freezing the user interface. Metaphorically, it is the Operator (like Tank)
outside the Matrix, running a program while you fight Agents, waiting for the right moment to pull you out.
- **CoroutineScope** (The Hovercraft): The defined boundary where coroutines can run safely.
Kotlin enforces a strict rule:
> **no coroutine without a scope**.

It authorizes tasks to start, determines when to cancel them, and handles cleanup.
If the hovercraft powers down, all operators inside are disconnected immediately.
- **launch** (The Jack-In): The function that physically starts the coroutine. `scope.launch {}`
fires off the asynchronous task (like showing a `Snackbar` that needs to wait 3 seconds before disappearing).


## Evolution: Legacy XML vs. Jetpack Compose
| Feature | Legacy Android (XML) | Jetpack Compose |
|---|---|---|
| **Toast Context** | Implicit. Usually just passed `this` inside an Activity. | Explicit. Requires `LocalContext.current` to bridge Compose with the OS. |
| **Snackbar UI** | Imperative. `Snackbar.make(view, "Text", Snackbar.LENGTH_SHORT).show()` | Declarative. Requires a `SnackbarHostState` hoisted to a `Scaffold`. |
| **Concurrency** | Handled implicitly under the hood by the View System. | Requires an explicit `CoroutineScope` to manage the lifecycle of the visibility delay. |
| **Positioning** | Frequently collided with Floating Action Buttons (FABs) unless manually padded. | Handled automatically by `Scaffold`. The FAB will beautifully slide up when the Snackbar appears. |

Toasts and Snackbars are the polite whisperers of Android UX—delivering brief, lightweight feedback
without interrupting whatever the user is doing. While a Toast remains a simple fire-and-forget OS tool,
the Snackbar in Compose represents a masterclass in state management. It forces you to think about
UI not as a sequence of commands, but as a reflection of state. If a user recklessly taps
"Format Hard Drive", whispering a three-second Toast at the bottom of the screen won't cut it.
That is where Dialogs take the stage—the modal Agents designed to block the screen and force a decision
before the simulation collapses.
