:::tip State-Driven Architecture
**The Technical Explanation*:
State-Driven Architecture is a paradigm where the User Interface is strictly a visual representation of the current data (state).
Instead of giving imperative commands to the UI (e.g., "animate out screen A, animate in screen B"), you simply update a state variable.
The UI framework automatically observes this change and re-renders itself to match the new state.
Navigation becomes a byproduct of state mutation.

**The Metaphorical Explanation**:
Imagine a digital billboard on a highway. You don’t command the billboard to "transition from the burger ad to the car ad."
You simply change the USB drive plugged into it (the state). The billboard has no memory of the burger ad;
it just faithfully displays whatever file is currently on the drive. If you change the file, the display changes instantly.

:::


## Intro

Welcome to the budget-friendly Venus Space Program! Since we spent our entire engineering budget on rocket fuel
and heat shields, we have exactly zero dollars left for fancy navigation libraries. This app simulates
a highly questionable interplanetary mission. You start at the Launchpad to slap a name tag on your brave
(or doomed) astronaut. Next, you blast off to Venus Orbit, where things get a bit toasty,
before finally making a touchdown on the acid-washed Surface.
It’s a fast-tracked journey to melting your spaceship, built entirely with pure Kotlin state.
No safety nets, no complex XML navigation graphs—just good old-fashioned state variables calling the shots!

Here is the structural breakdown of how this application operates:

### 1. Defining the Trajectory (Data Model)

`MissionPhase` (`Enum`):

Acts as the map for the app. It defines every possible location the user can be in
(`LAUNCHPAD`, `ORBIT_TRANSIT`, `VENUS_SURFACE`). This replaces the need for complex navigation graphs
found in standard NavHost implementations.

### 2. Mission Control (The Router)
`VenusMissionControl` (Composable): The brain of the application.
It gathers and manages all shared state (a concept called State Hoisting).

- State Management (`remember { mutableStateOf(...) }`):
Holds the active screen (`currentScreen`) and the payload data passed between screens (`astronautName`).
- The `when` Expression: Evaluates the `currentScreen` variable and decides which Composable to render.
Changing this variable triggers automatic recomposition, seamlessly swapping the screens.
- BackHandler: Intercepts the physical system Back button. Since this app lacks a built-in backstack,
returning to a previous screen is simulated by manually resetting the `currentScreen` state.


### 3. The Screens (Views)
The screens are completely isolated and blind to the navigation system.
Their only job is to display the UI based on provided data and bubble up user actions via callbacks (lambdas).
- `LaunchpadScreen`:
    - Maintains its own local state just for the text input field (`inputName`).
    - Fires an `onLaunchClick` callback, passing the astronaut's name up to the router, which saves it and flips
  the screen state to `ORBIT_TRANSIT`.
- `OrbitScreen`:
    - A purely "stateless" intermediate screen. Data like the commander name is injected directly from the parent router.
    - Provides two exit callbacks: `onLandClick` (proceeds to the surface) and `onAbortClick` (retreats to Earth).
- `VenusSurfaceScreen`:
    - The final destination. Displays the payload and provides an `onReturnHomeClick` callback.
    - Triggering this callback not only changes the screen state back to LAUNCHPAD but also clears the payload (astronautName = "").

### 4. Ground Control (Entry Point)
`MainActivity`: Sets up the Compose environment and Material Theme.
Its only visual job is laying down the background Surface and launching the `VenusMissionControl` router.


:::tip Unidirectional Data Flow (UDF)
**The Technical Explanation**:
UDF is a design pattern where data has only one way to travel: State flows down from a single source of truth
(a parent component or ViewModel) to the UI components (children). Conversely, events (user interactions like clicks or text input)
flow up from the children to the parent. The children never mutate the state directly; they only request a change,
ensuring the parent maintains total control over the data.

The Metaphorical Explanation:
Think of ordering food at a high-end restaurant. The kitchen (the source of truth) sends the food down to your table (the UI).
You are not allowed to walk into the kitchen and cook your own dessert (mutating state directly). Instead,
if you want something, you send a request up to the waiter (an event). The kitchen receives your request, bakes the cake,
and sends the new plate down to your table.

:::




Review the complete, working implementation of a multi-screen space mission application below.
Notice that we are not using any external navigation libraries, XML graphs, or complex `NavHost`
containers—just pure Kotlin state, basic components, and a `when` expression.

```kotlin
import android.os.Bundle
import androidx.activity.ComponentActivity
import androidx.activity.compose.BackHandler
import androidx.activity.compose.setContent
import androidx.compose.foundation.layout.*
import androidx.compose.material3.*
import androidx.compose.runtime.*
import androidx.compose.ui.Alignment
import androidx.compose.ui.Modifier
import androidx.compose.ui.unit.dp

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            MaterialTheme {
                Surface(
                    modifier = Modifier.fillMaxSize(),
                    color = MaterialTheme.colorScheme.background
                ) {
                    VenusMissionControl()
                }
            }
        }
    }
}

```

## Meta-Theatrics: The Holodeck vs. The Hallway
In classical Android development, navigating between screens (`Activities`) was like physically walking down
a corridor and opening heavy steel airlocks. To go from Earth to Venus, you had to pack your bags,
exit the Earth room, walk down the OS hallway, and enter the Venus room.

In Jetpack Compose, using State-Driven Navigation is like standing inside a
Star Trek Holodeck (or a theater stage). You never actually leave the room (`MainActivity`).
When you press "Launch", the director (VenusMissionControl) simply claps their hands, the stage crew instantly
rips down the cardboard cutout of Earth (LaunchpadScreen leaves the Composition), and drops a yellow,
sulfuric backdrop of Venus right in front of you (`OrbitScreen` enters the `Composition`).
