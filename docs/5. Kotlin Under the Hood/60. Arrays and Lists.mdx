# Project 04: The Player's Inventory (Arrays & Lists)
Before we can slay the dragon, we need a place to store our health potions, rusty swords,
and useless quest items. In our 4W2H Data Logistics model, this brings us to the 2W.
WHERE dimension: where do the data structures physically live, and how do they behave in memory?

Let's start top-down with a fully functional RPG inventory system.
Read the code below and observe how our hero's backpack adapts as the adventure progresses.


## The Goal: Dynamic Inventory System

Following our Top-Down approach, let's look at a fully functional inventory system.
Read the code and observe how the warehouse expands and shrinks as items are added or removed.

```kotlin
fun main() {
    println("--- 🎒 Inventory Booting ---")

    // 1. Spawning the dynamic storage
    val inventory = mutableListOf("Health Potion", "Wooden Shield", "Map")
    println("Initial Loadout: $inventory")

    // 2. Looting a chest (Create)
    inventory.add("Excalibur")
    println("After Boss Loot: $inventory")

    // 3. Upgrading an item (Update)
    inventory[1] = "Iron Shield" // Upgrading the Wooden Shield
    println("After Blacksmith Visit: $inventory")

    // 4. Consuming items (Delete)
    inventory.remove("Map")      // Dropped by item name
    inventory.removeAt(0)        // Consumed by physical index (Health Potion)

    println("Final Loadout: $inventory")
}
```

The Engineer's Question: If you run this code, the list magically grows and shrinks.
But what happens if our hero decides to pick up 10,000 rocks? Does the computer load all 10,000 rocks into
memory instantly, or does it wait until the player opens their bag?

To answer this, we must deconstruct these storage units using the 4W2H framework.

## Deconstructing Eager Structures via 4W2H

Kotlin provides three primary types of "inventory slots," all of which operate on the Eager Paradigm.
In the standard 4W2H model, eager evaluation is compared to an "All-You-Can-Eat Buffet"
where the cooks prepare all the meals before the guests even arrive.
In gaming, this means pre-loading the entire map into RAM instantly.

Let's break down how Arrays and Lists fit into our data logistics.

### 1. The Rigid Lockers: `Array`

An Array is the most primitive and rigid data structure.

How it works:
- It has a strictly fixed size.
- Once you build a 5-locker array, you cannot add a 6th locker, and
- you cannot destroy the 3rd locker.
- The Rule: The size is immutable, but the contents of the lockers can be changed.

```kotlin
val numbers = arrayOf(1, 2, 3, 4, 5)

// Reading from a specific locker (Index starts at 0!)
println(numbers[0])  // Prints: 1
println(numbers[2])  // Prints: 3

// Updating the content of locker 1
numbers[1] = 10
println(numbers[1])  // Prints: 10
```

### 2. The Display Case: Read-Only List
A Read-Only List is a modern, safer collection.

How it works:
- It is an ordered collection of elements.
- Duplicates are allowed.
- The Rule: It is strictly immutable (read-only).

Once the display case is built and filled, you cannot add, update, or remove anything.
It is permanently locked. This makes it incredibly safe and fast for the CPU to process.

```kotlin
val fruits = listOf("Apple", "Banana", "Orange")

println(fruits[0])  // Prints: Apple

// Using our forklift (loop) to scan the display case
for (fruit in fruits) {
    println(fruit)
}
// fruits.add("Kiwi") -> 🔴 ERROR! The list is locked.
```

### 3. The Shopping Cart: `MutableList`

This is the structure we used in our starting goal.

How it works:
- It is fully dynamic.
- It manages its own memory, growing and shrinking as needed.
- The Rule: It supports full CRUD operations (Create, Read, Update, Delete).

```kotlin
val mutableFruits = mutableListOf("Apple", "Banana", "Orange")

// CREATE
mutableFruits.add("Grapes")

// READ
println(mutableFruits[0])

// UPDATE
mutableFruits[1] = "Strawberry"

// DELETE
mutableFruits.remove("Banana") // Deletes the first matching value
mutableFruits.removeAt(1)      // Deletes the item at the exact position

```

##  The 4W2H Model

### 0. WHAT: The Payload
- We are processing primitives or complex objects.
- In our code, these are simple String objects (like "Excalibur").
- They act as the "Sticky Notes" of data—short, simple information bits.

### 1. WHERE: State & Storage
- These data structures live in temporary, local memory.
- Our inventory variable is a local variable, which functions like a "Pocket".
- Only the current scope has access to it, and the data will vanish once the function finishes executing.

### 2. WHEN: Evaluation Strategy
These structures are strictly Eager. When you call `arrayOf()` or `listOf()`,
the CPU calculates and loads all data at once. If you create a list of 10,000 items, the processor processes
all 10,000 immediately. This requires a significant amount of RAM on startup, much like spawning every NPC
in the game world at the exact moment the level loads.

### 3. WHO & HOW: Access and Reactivity
Depending on which specific eager structure you choose,
the flow of data changes:
- The Rigid Grid (`Array`): Arrays are like the classic, unforgiving inventory
grid in Resident Evil. It has a strictly fixed size. You can swap a green herb for a red herb (update),
but you cannot add a brand-new slot to the grid. It acts as a "Silent Ledger" — the UI won't automatically
know if you change an item; you have to manually check it.
- The Lore Book (`List`): A read-only list is immutable. Once the developer writes the lore book,
the player can only read it. It is entirely locked,
preventing accidental bugs and making it blazing fast for the CPU to iterate over.
- The Bottomless Bag (`MutableList`): This is our dynamic inventory from the code above.
It expands and contracts automatically. It allows full CRUD operations (Create, Read, Update, Delete),
meaning the player dictates the pace by pulling or pushing data into the bag.

### 4. HOW LONG: Lifecycle
Because these structures are stored in standard RAM, they represent "Short-term Memory".
If you restart the application (or your character dies and the game crashes), this specific inventory state
is lost forever. To survive a reboot, this data would need to be moved to "The Safe"—a permanent database
or hard drive save file.

:::tip Engineer's Choice
Always default to using a Read-Only List (listOf).
Only upgrade to a MutableList if your application strictly requires adding or removing items dynamically.
Locking data prevents accidental bugs!
:::

## Summary
:::tip Arrays vs. Lists in Kotlin

The primary difference comes down to **resizability** and **element mutability**.
- `Array` always has a fixed size, whereas
- lists in Kotlin are separated into two distinct interfaces:
    - read-only (`List`) and
    - modifiable (`MutableList`).

| Feature | `Array` | `List` (Read-only) | `MutableList` |
| :--- | :--- | :--- | :--- |
| **Size** | Fixed (no `add`/`remove`) | Fixed | Dynamic (has `add`/`remove`) |
| **Element Mutability** | Yes (`arr[0] = 1`) | No | Yes (`list[0] = 1`) |
| **Under the hood (JVM)**| Native arrays (e.g., `Integer[]`, `int[]`) | `java.util.List` | `java.util.ArrayList` |

**Syntax in practice:**

```kotlin
// 1. Arrays (Fixed size, mutable elements)
val array = arrayOf(1, 2, 3) // create
array[0] = 99                // update
// array.add(4)              // ERROR

// 2. Read-only Lists (Immutable view)
val list = listOf(1, 2, 3)   // create
// list[0] = 99              // ERROR: set() method
// list.add(4)               // ERROR: no size-modifying methods

// 3. Mutable Lists (Dynamic size, mutable elements)
val mutableList = mutableListOf(1, 2, 3)  // create
mutableList[0] = 99           //  update
mutableList.add(4)            // add/update
```
