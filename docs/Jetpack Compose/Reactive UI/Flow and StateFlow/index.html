Flow and StateFlow

In Lesson 1, we built our ClassroomCheckInScreen using Jetpack Compose state:

@Composable
fun ClassroomCheckInScreen() {
    var studentName by remember { mutableStateOf("") }
    var presentStudents by remember { mutableStateOf(listOf<String>()) }
    // ...
}

And then, disaster struck. When we rotated the screen, Android destroyed and rebuilt our Activity, wiping out our entire list of presentStudents.

To fix this, we need to move our data out of the UI and into a separate, safe Kotlin class that survives screen rotations (which we will meet in next Lesson as the ViewModel).

Before we build that class, we need to answer a critical architectural question—and test our new tools in a simple Kotlin console app!

1. The Big Question: Why Not Just Move mutableStateOf?​

If mutableStateOf already tells Jetpack Compose when to redraw the screen, why can't we just move mutableStateOf into our backend logic class and call it a day? Why do professional Android developers use Flow and StateFlow instead?

Because mutableStateOf belongs to Jetpack Compose (the UI), while our business logic should be written in pure Kotlin.

FeaturemutableStateOfStateFlow
Where it belongs🎨 UI Layer (Jetpack Compose)🧠 Logic Layer (ViewModel / Pure Kotlin)
DependencyTied strictly to Compose UI libraries.Pure Kotlin Coroutines (kotlinx.coroutines). Works anywhere!
Thread SafetyGood for UI, but lacks built-in atomic updates like .update {} for complex background operations.Built for heavy concurrency, background threads, and safe state updates.
SuperpowersGreat for simple UI states (e.g., is a dialog open? what did the user type right now?).Can be combined, filtered, mapped, and connected directly to databases (Room) and networks (Retrofit/Ktor).
Rule of Thumb

Use remember { mutableStateOf(...) } for temporary UI widget state (like whether a password text field is visible or hidden). Use StateFlow for screen and business state (like the list of checked-in students, user profiles, or database items).

2. Lab 1: The "Silent Variable" Problem​

Let's leave Jetpack Compose for a moment and open a pure Kotlin console (you can paste these examples directly into play.kotlinlang.org!).

Why can't our logic class just use a normal Kotlin var? Let's test it:

fun main() {
    // A standard Kotlin variable
    var presentStudents = listOf<String>()

    // The UI checks the list once when the app starts
    println("📱 Screen shows: $presentStudents")

    // Later, students check in...
    presentStudents = presentStudents + "Alice"
    presentStudents = presentStudents + "Bob"

    // Nothing prints! The screen has no idea the variable changed.
}

Console Output:

📱 Screen shows: []

A standard var is passive. When you change it, it stays silent. Nobody notifies the screen to redraw. We need a variable that shouts whenever its value changes!

3. Lab 2: Enter Flow (The Conveyor Belt)​

To make data reactive in pure Kotlin, we use Coroutines Flow. Think of a standard function fun getStudents(): List<String> as handing you a single box of items. A Flow, on the other hand, is a running conveyor belt that pushes items to you one by one over time.

tip

Think of a coroutine like a smart restaurant waiter.

A traditional thread is like a waiter who takes your order, walks to the kitchen, and stands there doing absolutely nothing until your food is ready.

A coroutine is a smart waiter who sends the order to the kitchen (a suspension point like a network call or delay), remembers where they left off, and immediately goes to serve other tables. When your food is ready, they seamlessly return to finish serving you. This is why you can run 100,000 coroutines simultaneously on just a handful of underlying threads without crashing your app.

Preparations:

  • Make a new project in InteliJ
  • Add a new library in the file build.gradle.kts
dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.8.0")
}

Let's run a simple Flow in the console:


import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.time.Duration.Companion.seconds

// 1. Building the Conveyor Belt (Cold Flow)
fun studentCheckInStream(): Flow<String> = flow {
    println("🚪 Doors are open! Waiting for students...")
    delay(2.seconds) // Wait 1 second
    emit("Alice") // Put Alice on the conveyor belt

    delay(2.seconds)
    emit("Bob")   // Put Bob on the conveyor belt

    delay(2.seconds)
    emit("Charlie")
}

fun main() = runBlocking {
    // 2. Turning on the belt and watching items arrive using .collect
    studentCheckInStream().collect { student ->
        println("🔔 DING! $student just walked in!")
    }
}

Console Output (printing line by line every second):

🚪 Doors are open! Waiting for students...
🔔 DING! Alice just walked in!
🔔 DING! Bob just walked in!
🔔 DING! Charlie just walked in!

How does it work?​

  • emit(): Pushes a new value into the stream.
  • collect { ... }: Listens to the stream. Every time emit() pushes a value, the code inside collect wakes up and runs automatically!
runBlocking

Think of runBlocking as a bridge between the normal Kotlin world and the Coroutine world.

To understand why we need it, you have to know one important rule about Kotlin:

Normal functions cannot call suspend functions. If you try to call delay() or .collect() inside a plain main() function, IntelliJ will give you a red error because normal functions don't know how to pause and resume.

You need to create a "Coroutine Scope" (a safe space for coroutines to run).

Here is exactly what runBlocking does:

Cold Streams vs. Hot Streams

A standard flow { ... } is called a Cold Stream—just like a Netflix movie. It doesn't start playing until someone presses Play (calls .collect()). And if a second person presses Play 5 minutes later, the movie starts from the very beginning for them.

4. Lab 3: StateFlow (The Live Scoreboard)​

A Cold Flow is great for loading data, but for a User Interface, a Netflix movie isn't what we need.

Imagine you rotate your phone screen:

  1. You don't want to replay every single student check-in from the beginning of the day with a 1-second delay.
  2. You want to immediately see the current list of students right now!
  3. You also want to be able to add a new student whenever a button is clicked.

For this, we need a Hot Stream that holds a single current value and remembers it. We need StateFlow (and its changeable twin, MutableStateFlow).

Let's simulate our Classroom Check-In app purely in the console using MutableStateFlow:

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun main() = runBlocking {
    // 1. Create a MutableStateFlow holding our initial empty list
    val presentStudentsFlow = MutableStateFlow(listOf<String>())

    // 2. Simulate the UI listening to the state in the background
    val uiCollectorJob = launch {
        presentStudentsFlow.collect { currentList ->
            println("📱 UI REDRAWN! Present students (${currentList.size}): $currentList")
        }
    }

    delay(500) // Give the collector a moment to start

    // 3. Simulate user clicking the "Check In" button!
    println("\n👉 Action: Checking in Alice...")
    presentStudentsFlow.update { currentList -> currentList + "Alice" }
    delay(1000)

    println("\n👉 Action: Checking in Bob...")
    presentStudentsFlow.update { currentList -> currentList + "Bob" }
    delay(1000)

    println("\n👉 Action: Checking in Charlie...")
    presentStudentsFlow.update { currentList -> currentList + "Charlie" }
    delay(500)

    uiCollectorJob.cancel() // Stop the simulation
}

Console Output:

📱 UI REDRAWN! Present students (0): []

👉 Action: Checking in Alice...
📱 UI REDRAWN! Present students (1): [Alice]

👉 Action: Checking in Bob...
📱 UI REDRAWN! Present students (2): [Alice, Bob]

👉 Action: Checking in Charlie...
📱 UI REDRAWN! Present students (3): [Alice, Bob, Charlie]

Look closely at what just happened:​

  1. Immediate Initial State: As soon as collect started, it immediately printed [] without waiting. StateFlow always has a value!
  2. Automatic Reaction: We wrote println("📱 UI REDRAWN!...") only once. Every time we called .update { ... }, the collector automatically woke up and printed the new state.
  3. Safe Updates with .update {}: Inside .update { currentList -> currentList + "Alice" }, Kotlin gives us the guaranteed latest list (currentList), creates a new list with the added student, and broadcasts it.

5. Lab 4: Building the "Vault" in Pure Kotlin​

Before we jump into Android's ViewModel in Lesson 2, let's wrap our MutableStateFlow inside a clean Kotlin class.

There is one rule: The UI should never be allowed to modify the state directly. Only our class can update the list; the outside world can only read and listen to it.

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

class ClassroomVault {
    // 🔒 PRIVATE: Only ClassroomVault can change this!
    private val _presentStudents = MutableStateFlow(listOf<String>())

    // 🌍 PUBLIC: Anyone (like the UI) can listen, but nobody can overwrite it!
    val presentStudents: StateFlow<List<String>> = _presentStudents.asStateFlow()

    // 🔘 EVENT FUNCTION: The UI calls this when the user clicks the button
    fun checkInStudent(name: String) {
        if (name.isBlank()) return // Validation!
        _presentStudents.update { currentList -> currentList + name }
    }
}

fun main() = runBlocking {
    val vault = ClassroomVault()

    // The UI listens to the public read-only StateFlow
    val uiJob = launch {
        vault.presentStudents.collect { students ->
            println("📱 Screen updated: $students")
        }
    }

    delay(500)
    vault.checkInStudent("Alice")
    delay(500)
    vault.checkInStudent("") // Ignored by validation!
    vault.checkInStudent("Bob")
    delay(500)

    // ❌ Try uncommenting the line below - it won't even compile!
    // vault.presentStudents.update { emptyList() } // ERROR! It's read-only!

    uiJob.cancel()
}
Spoiler Alert for Lesson 2!

Look at the ClassroomVault class above. In Lesson 2, we are going to take this exact pattern, add : ViewModel() to the class header so Android protects it during screen rotations, and connect it to our ClassroomCheckInScreen!
